# BaseBlobs Project Rules & Guidelines

## Rules for New Paid Features / Economy Actions

Любое новое действие, которое тратит или начисляет кубы/энергию/предметы/статус игрока, реализуется **только** так:

1. **Server-Side Transaction Authority**:
   - Новый `type: '...'` в `api/claim.ts` — сервер читает баланс из `saves` (никогда не из тела запроса), сам проверяет условия, сам списывает/начисляет, сам пишет через Admin SDK внутри `db.runTransaction`.

2. **Client Intent Only**:
   - Фронт только шлёт "намерение" (`{ type, ...параметры выбора, sessionToken }`) и получает готовый обновлённый стейт в ответ — никогда не мутирует `cubes`/`energy`/`blobs`/`hasX` в локальном state напрямую перед запросом (кроме чисто оптимистичного UI-апдейта, который откатывается при ошибке).

3. **Strict Firestore Security Rules**:
   - Соответствующая Firestore-коллекция по умолчанию `allow write: if false` — открывать `write: if true` для новой коллекции нельзя ни на "временно", ни "потом закрою". Если нужен прямой клиентский write — обсуждать отдельно, это исключение, а не дефолт.

4. **Security Verification Check**:
   - Проверка перед мерджем любой новой платной фичи: "если открыть devtools и вызвать Firestore/`/api/claim` напрямую, минуя UI, можно ли получить предмет/бонус дешевле или бесплатно?" — если да, фича не готова к релизу.

## Rules for Wallet Interaction

5. **Wallet Interaction Discipline**:
   - Любой **автоматический** вызов сервера (`useEffect` на монтирование, `setInterval`, обработчики `focus` / `visibilitychange` / `online`, любой поллинг и ретрай) обязан ходить только через `fetchWithSession(..., { interactive: false })` и корректно обрабатывать `null` в ответе. `null` означает "живой сессии нет" — это нормальный ожидаемый случай, надо тихо выйти, а не показывать ошибку.
   - `interactive: true` (значение по умолчанию) допустимо **исключительно** в обработчике клика пользователя.
   - Незапрошенное окно подписи — это флаг Safe Browsing / MetaMask / Blockaid, а не косметика. Проект уже был помечен как "опасный" именно за повторные бессмысленные обращения к кошельку.
   - Проверка перед мерджем: "если сессия истекла и игрок просто переключился на вкладку — откроется ли кошелёк?" Если да, фича не готова к релизу.

## Rules for Persisted Identifiers

6. **Никогда не переименовывать id, попавшие в сохранения**:
   - Строковые id, записанные в документы Firestore (`saves`, `nodes`, `reactor_*`), — это часть формата данных, а не текст интерфейса. Их переименование обнуляет прогресс игроков.
   - Конкретный случай: ветка апгрейда `id: 'harvest'` **отображается как "Extraction"**, но id менять нельзя — у игроков в сохранениях лежат купленные уровни под ключом `harvest`. То же касается `speed` / `fortune` и любых id зон, событий, тиров нод.
   - Менять можно свободно: `name`, `icon`, `desc`, `color`, `kind` — они живут только в статическом конфиге `src/data.ts` и никуда не сохраняются.
   - Если переименование id всё же необходимо, оно требует отдельной миграции на сервере с переносом старых ключей, а не простого sed по проекту.

## Rules for Blob Upgrade Branches

7. **Набор веток роллится только на сервере**:
   - `rollBlobBranches()` вызывается исключительно в `api/claim.ts` при создании блоба. Клиент никогда не выбирает и не досылает ветки.
   - При покупке апгрейда сервер обязан сверять ветку со списком **из сохранения блоба** (`getBlobBranches(blob)`), а не из тела запроса. Иначе через devtools можно прокачать невыпавшую ветку.
   - Проверка перед мерджем: "если подменить `branch` в запросе к `/api/claim`, прокачается ли ветка, которой у блоба нет?" — если да, фича не готова к релизу.
